# Shared maintenance preflight

Resolve or reuse the root and environment context once at the entrypoint. Strictly read-only analysis does not require Python until a Python helper is needed. Complete the runtime preflight before the first repository mutation (including checkout, preparation, application, merge or commit) or first Python helper, whichever comes first. Child skills reuse the parent context rather than restarting preflight. Never install software during maintenance.

- Retain the real root from `git rev-parse --show-toplevel`; require success and the intended repository, then work from that root throughout.
- Freeze the environment as `local_windows`, positively identified Codex `cloud`, or `other` only when neither applies. Retain host evidence: Linux or a branch named `work` alone never proves Codex Cloud. Inspect unknown hosts before granting environment-specific capabilities.
- Resolve and freeze the absolute Python 3 executable as `<PYTHON>` only at that first mutation/helper gate, then reuse it throughout the workflow and child skills. Read-only PR URL validation, compact metadata and changed paths do not need Python. Direct physical installation needs only the root, host and Windows install capabilities, not Python or SVN.
- Retain capability states: Git, PR-only `gh`, library-only SVN, physical installation, and required environment fallbacks. Distinguish not needed/not checked from available or unavailable. Resolve a newly required capability once at its gate; do not probe unused tools.
- Physical installation is eligible only on local Windows. At the install stage check the existing installer and AddOns paths once; child skills reuse that result. Cloud/Linux offers no menu and never loads the installation implementation.

Recheck only a fact invalidated by an observed failure, changed checkout/ref or explicit environment change; explain why and retain unaffected facts. Failed checks remain errors, never no-ops. If the retained Python disappears, stop rather than silently reselecting.

Bootstrap `scripts/maintenance_runtime.py` using an available interpreter: on Windows try `py -3`, `python`, then `python3`; on Linux try `python3`, then `python`. The central resolver actually executes candidates, rejects Python 2, and prints only the absolute Python 3 executable. Check its exit status and retain that output once per workflow. If aliases cannot launch the bootstrap, a discovered, already installed absolute interpreter (including a Codex bundled runtime) may launch it; never hardcode a user's bundled path. Its Python-2-parseable bootstrap can locate Python 3 through an older alias, but Python 2 is never selected. If no bootstrap or no valid Python 3 exists, stop before changing branches.

Example bootstrap: `python3 scripts/maintenance_runtime.py` on Linux or `py -3 scripts/maintenance_runtime.py` on Windows. Thereafter use only the retained runtime for `<PYTHON> scripts/prepare_update.py [--cloud-work]`, `<PYTHON> scripts/classify_lib_changes.py --base <base> --target upstream/main` and `<PYTHON> scripts/check_lib_updates.py [--apply <approved-name>]`. Quote absolute paths; PowerShell needs the call operator `&`. Reuse the runtime throughout the parent and child workflows. If it becomes unavailable, stop rather than reselecting.

Validate `git --version` once before Git maintenance; validate `svn --version --quiet` once when an explicit or approved library check first requires it (current `.pkgmeta` includes SVN). Reuse successful parent checks. Missing tools are errors. `gh` is only required for the existing upstream PR metadata/diff workflow. Python helpers use only the standard library. Lua and PowerShell are not Cloud maintenance dependencies; PowerShell is only needed for local Windows installation.

Cloud/Linux syncs both branches independently to full `upstream/main` HEAD. After verified publication, report sync complete and installation as a local Windows step; offer no installer. Windows offers the existing menu only when the installer and AddOns directory exist and the approved remote ZIP is available. Inspect unknown environments before offering installation.

Load [Cloud configuration](cloud-environment.md) only for verified Cloud checkout preparation or missing required SVN setup on Cloud/Linux. Do not load its bootstrap on local Windows. Retain any required PATH/runtime fallback after setup; setup failure remains pending.

For a direct library or PR entrypoint, inspect the branch once when branch-dependent work is needed. Read-only PR URL validation, compact metadata and changed paths may precede runtime/checkout preparation. Before a Python helper or repository mutation, complete the runtime preflight. On `new-features`, reuse parent preparation without another fetch. Only positively identified Codex Cloud `work` loads the [development checkout adapter](cloud-environment.md#checkout-preparation) before work requiring the real development checkout. Local Windows keeps its `new-features` gate; other branches stop for review. Update retains default `--mode update` and independent full-HEAD sync gates.
