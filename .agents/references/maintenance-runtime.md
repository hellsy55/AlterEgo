# Shared maintenance preflight

Run from the repository root before branch setup, checkout, merge or library action. Never install software during maintenance. Keep the resolved runtime in workflow state across tool calls and child skills; `<PYTHON>` always means that same absolute executable.

Bootstrap `scripts/maintenance_runtime.py` using an available interpreter: on Windows try `py -3`, `python`, then `python3`; on Linux try `python3`, then `python`. The central resolver actually executes candidates, rejects Python 2, and prints only the absolute Python 3 executable. Check its exit status and retain that output once per workflow. If aliases cannot launch the bootstrap, a discovered, already installed absolute interpreter (including a Codex bundled runtime) may launch it; never hardcode a user's bundled path. Its Python-2-parseable bootstrap can locate Python 3 through an older alias, but Python 2 is never selected. If no bootstrap or no valid Python 3 exists, stop before changing branches.

Example bootstrap: `python3 scripts/maintenance_runtime.py` on Linux or `py -3 scripts/maintenance_runtime.py` on Windows. Thereafter use only the retained runtime for `<PYTHON> scripts/prepare_update.py [--cloud-work]`, `<PYTHON> scripts/classify_lib_changes.py --base <base> --target upstream/main` and `<PYTHON> scripts/check_lib_updates.py [--apply <approved-name>]`. Quote absolute paths; PowerShell needs the call operator `&`. Reuse the runtime throughout the parent and child workflows. If it becomes unavailable, stop rather than reselecting.

Validate `git --version` before Git maintenance; validate `svn --version --quiet` before an explicit or approved library check (current `.pkgmeta` includes SVN). Missing tools are errors. `gh` is only required for the existing upstream PR metadata/diff workflow. Python helpers use only the standard library. Lua and PowerShell are not Cloud maintenance dependencies; PowerShell is only needed for local Windows installation.

Cloud/Linux syncs both branches independently to full `upstream/main` HEAD. After verified publication, report sync complete and installation as a local Windows step; offer no installer. Windows offers the existing menu only when the installer and AddOns directory exist and the approved remote ZIP is available. Inspect unknown environments before offering installation.

See [Cloud configuration](cloud-environment.md).

For a direct library or PR entrypoint, after preflight inspect the current branch. Only when the host is positively identified as Codex Cloud and the branch is `work`, run `<PYTHON> scripts/prepare_update.py --mode development --cloud-work` once and require success and the real `new-features` branch before any library checker/apply or PR analysis/application/commit. This uses the same canonical preparation as update, but fetches only `origin/new-features` with an explicit destination, creates only its missing tracking branch, and leaves `main` and `upstream` untouched. It preserves `work`, rejects dirty or unpublished/divergent work before switching, and never resets, merges, commits or pushes. On local Windows, keep the existing `new-features` requirement; never pass `--cloud-work`. If already on `new-features` (including a child skill), reuse the parent state without running preparation or fetching again. Existing local `new-features` history is preserved: after bootstrap compare it with `origin/new-features`; stop on divergence, and review any pre-existing unpublished commits and obtain explicit publication approval before any eventual push. A report-only library check does not authorize publishing that history. Other branches stop for review. Update retains the default `--mode update` preparation and independent full-HEAD sync gates.
