# Vendored library version check

Run on `new-features` from the repository root. Complete or reuse the parent workflow's [maintenance preflight](../../references/maintenance-runtime.md), including retained `git` availability and a one-time `svn` check if not already checked. Use its retained absolute `<PYTHON>` executable for every checker invocation; never resolve again in a child skill. Reuse a valid report-only checker result only within the workflow while its relevant inputs remain valid: invalidate it if `.pkgmeta`, `.pkgmeta-lock.json` or the relevant first-level directory structure under `Libs/` changes, since the checker also reports orphan directories. Internal library content changes alone do not invalidate the result unless they change an input used by the checker. Retain a compact first-level directory-name list and compare it only when reuse requires validation; do not recursively scan or hash library contents. Rerun after any invalidating change, an observed failure or a requested refresh.
Before step 1, follow the shared preflight reference's direct-entrypoint development preparation when starting on verified Codex Cloud `work`; require the real `new-features` branch before checker/apply. Reuse existing parent preparation without another fetch. Local Windows keeps its existing branch gate.

1. Run `<PYTHON> scripts/check_lib_updates.py` without arguments, unless a valid parent result is already retained. This is report-only and changes nothing. Its inputs are this branch's `.pkgmeta`, the committed `.pkgmeta-lock.json` and the first-level `Libs/` directory names used for orphan reporting.
2. Read the compact `LIBS`, `CHECKED`, and `UNKNOWN` summary. The script still resolves and compares every `.pkgmeta` external against the lockfile and still reports every pending or unknown entry; only successful per-library lines are omitted. If there are no pending or unknown updates, report that briefly in Portuguese and continue the parent workflow immediately. If `UNKNOWN` is nonzero, the checker exits nonzero; never claim all libraries are current. Report the lookup failure and URLs, and follow the existing unknown-entry continuation rule. Other nonzero errors stop the library action; never interpret them as no pending updates. For a standalone check, finish without syncing or installing. Do not list current libraries individually.
3. If any library is marked `[!]`, read [pending updates](references/pending-updates.md) before recommending or applying anything. Wait for explicit library choices. If a library is marked `[?]`, report that it could not be checked automatically, give its `.pkgmeta` URL for manual checking, and continue the rest of the workflow.
4. If the output flags directories under `Libs/` absent from `.pkgmeta`, mention them as informational. The checker does not check or update those directories. Never delete or change them automatically; they do not block the workflow.

Read [why libraries are vendored](references/vendoring.md) only when branch setup, ignored files, ZIP installation, or library ownership needs explanation. Never edit `.pkgmeta-lock.json` by hand.
