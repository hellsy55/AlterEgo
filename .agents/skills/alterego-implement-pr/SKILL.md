# Implement an upstream PR

Use for an upstream PR URL accompanied by a request to implement, apply, port, or evaluate it. Work on `new-features`.

1. Resolve or reuse only the root and environment context from [maintenance preflight](../../references/maintenance-runtime.md) at entry. Confirm the URL names a PR in `DennisRas/AlterEgo`; if it belongs to another repository, stop and ask before doing anything else. Strictly read-only URL validation, compact PR metadata and changed paths need no Python or checkout preparation. Check `gh` once when needed. Before any Python helper or repository mutation (checkout/preparation/application/merge/commit), complete or reuse the runtime preflight and retain `<PYTHON>` for all child skills. Work on `new-features`: before a library check or comparison against the development checkout, verified Codex Cloud `work` must pass the shared reference's development checkout adapter and reach real `new-features`. Reuse parent preparation without another fetch. Local Windows keeps its existing branch gate.
   For optional artifact delivery, record the full committed `new-features` SHA after any required checkout preparation and before this workflow's first change (including approved library changes). Preserve it as the immutable baseline; never substitute the state just before the PR commit.
2. Obtain compact metadata first with `gh pr view <url> --json number,title,changedFiles,additions,deletions,files`. Report the number, title, file count, additions, deletions, and affected areas/modules. Inspect changed paths before opening a diff. Treat `Libs/`, `.pkgmeta`, and `.pkgmeta-lock.json` as library triggers; an invalid or incomplete file list is an error, not proof of no library changes. If the user explicitly requested a library check with the PR, read and run [the library skill](../alterego-libs/SKILL.md) for the current branch. If the PR touches library paths or metadata, summarize that fact and offer to check the current branch's other vendored libraries for external updates; state that this check does not validate the PR's proposed library changes. Run it only if the user chooses yes. If updates are pending, preserve the library skill's PR-specific update-or-leave-as-is checkpoint. A PR with no library trigger proceeds without loading the library skill or running the checker.
3. Fetch the diff with `gh pr diff <url>` only after the path gate. Fetch full raw file contents only when the diff does not establish the practical effect, such as logic split across untouched sections, renamed symbols, or dependencies on other functions. Compare against the current `new-features` branch. Inspect proposed library files, pins, and lockfile changes directly when the PR touches them; assess their practical effect separately from any current-branch checker result. Never describe a current-branch check as validation of the PR. An unrelated PR may be analyzed and implemented while an undiscovered external library release exists; this is the accepted tradeoff of event-driven checks.
4. Before applying anything, explain in plain Portuguese what the fork gains, what existing behavior or customization it loses, and what remains unchanged. For an actual Git merge conflict, use [merge conflicts](../alterego-update/references/merge-conflicts.md): functional explanation and interaction first, then options and a user choice; show code only on request. For a large change without a technical conflict, offer apply as-is, apply with adaptation, skip that part, or apply nothing. For a smaller change, ask whether to apply or skip it. Wait for explicit confirmation of the chosen option. Do not treat a reviewer result as permission.
5. Apply only the chosen change. Commit with an English imperative subject and body, without AI signatures, and reference the PR number and source in the body. Before committing, follow the root `AGENTS.md` staged-list, staged-stat, complete-staged-diff, and explicit-approval checkpoint. Push the result to `new-features`.
6. Only after the final commit/push is complete and verified at `origin/new-features`, compare the immutable baseline with the final committed state. If no net functional installable changes remain, do not offer an incremental ZIP. Otherwise ask in Portuguese: "Deseja que eu gere também um ZIP incremental pronto para instalar?" If the user declines, finish normally; only acceptance authorizes the optional delivery below. Do not install or perform another commit/push for artifact delivery.

## Optional incremental installer delivery

This workflow owns its optional delivery independently; do not load or depend on `cloud-update-delivery.md`.

- Generate one `AlterEgo_<final-version>_installer.zip`, using the final short SHA instead of the version when unreliable. Compare the baseline with the final committed state and include only eligible added or modified addon runtime files with their final committed contents; omit unchanged or reverted files. Exclude infrastructure, documentation, AGENTS, tooling, tests, temporary files, and other non-installable content. Include changed library runtime content only when actually part of the final net difference; packaging never triggers a library check.
- Map repository-root addon paths to `AlterEgo/...` for extraction over `Interface/AddOns`, without an outer wrapper. Never put deletions or artificial deletion files inside the ZIP; list required manual removal paths separately in Portuguese. If no eligible added or modified runtime files remain, do not generate an empty ZIP or upload anything; report any manual removals separately.
- Preserve normal Codex artifact delivery. Before uploading, confirm the final ZIP exists, has a nonzero byte size, passes archive integrity validation, and contains at least one valid installable file. Reuse or calculate local SHA-256 when inexpensive and available. Upload the exact same completed ZIP; never regenerate or recreate a second version for Drive.
- Use only the official connected Google Drive plugin and its Google Drive skill. Verify the fixed destination `Codex Artifacts/AlterEgo` by folder ID `1jCguR4JmMM-MzCDUOqxb17040RmRzSUo` with `get_file_metadata`, then use `upload_file` with the final artifact's supported file reference, unchanged filename, MIME type `application/zip`, and that ID as `parent_folder_id`. Do not introduce rclone, manual OAuth, API keys, secrets, or external dependencies.
- After upload completes, use its returned file ID for a fresh `get_file_metadata` readback requesting `id,name,parents,size,webViewLink`. Confirm existence, the exact filename/title, and the destination folder ID in parents; require remote size to match the local byte size when available, and verify the returned link/ID when available. Do not require `trashed`, which may be absent from normalized metadata. An upload response alone is never success; report `Google Drive: OK` only after readback validates the metadata.
- Drive is only an additional post-generation delivery channel. If the plugin, upload, or readback fails or metadata does not match, preserve Codex delivery and report the actual error or failed verification separately from the completed main workflow. Never roll back, invalidate, or redo a successful commit/push, and never report false Drive success.

Report the verified PR outcome in Portuguese. When an installer ZIP exists, compactly report its filename, file count, local byte size, local SHA-256 when available, manual deletions or none, `Google Drive: OK` or the actual error, and the link/ID returned by Drive when available. If a required choice remains, report the task as pending.
